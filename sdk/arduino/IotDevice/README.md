# IotDevice — SDK для ESP32 и ESP8266

Arduino-библиотека для подключения ESP32 и ESP8266 к IoT Stack. Аналог `2smart-cloud-cpp-sdk`.

Что берёт на себя:
- **Привязку**: обменивает claim-токен на MQTT-учётку и хранит её (ESP32 — NVS, ESP8266 — файл в LittleFS).
  При новом токене привязывается заново.
- **Портал настройки**: точка доступа `IoT-XXXX` с формой для Wi-Fi, сервера и токена. Открывается сам, если чего-то не хватает.
- **MQTT over TLS**: проверка сертификата, NTP, LWT `lost`, переподключение с экспоненциальной задержкой (1 → 60 с).
- **Типизированные свойства**: `bool`, `int`, `float`, `string`. SDK сам собирает `$meta`, приводит и проверяет
  входящие команды, отправляет значения, накопленные офлайн, после переподключения.

Требования: библиотека **PubSubClient** (Nick O'Leary) и одна из плат:
- **ESP32** — Arduino core 3.x;
- **ESP8266** — Arduino core 3.x. TLS идёт через BearSSL и занимает около 20 КБ ОЗУ, поэтому оставьте
  скетчу запас памяти. Файловая система LittleFS нужна для хранения настроек: выберите в Tools → Flash Size
  вариант с FS хотя бы на 64 КБ.

## Установка

Сервер, к которому подключается библиотека: [iot-stack](https://github.com/andrk774/iot-stack).

**Arduino IDE:** скачайте [ZIP этого репозитория](https://github.com/andrk774/IotDevice/archive/refs/heads/main.zip)
и добавьте через Sketch → Include Library → Add .ZIP Library, затем установите PubSubClient через менеджер библиотек.
Примеры появятся в File → Examples → IotDevice.

**PlatformIO:**
```ini
[env:esp32dev]
platform = espressif32
board = esp32dev
framework = arduino
lib_deps =
  knolleary/PubSubClient@^2.8
  https://github.com/andrk774/IotDevice.git

[env:d1_mini]
platform = espressif8266
board = d1_mini
framework = arduino
board_build.filesystem = littlefs
lib_deps =
  knolleary/PubSubClient@^2.8
  https://github.com/andrk774/IotDevice.git
```

Стандартная платформа `espressif32` в PlatformIO ставит Arduino core 2.x, а SDK сверялся с API core 3.x.
На 2.x он, скорее всего, тоже соберётся, но это не проверялось. Для core 3.x в PlatformIO есть
платформа [pioarduino](https://github.com/pioarduino/platform-espressif32).

## Быстрый старт

```cpp
#include <IotDevice.h>

IotDevice device("Кухня", "1.0.0");

IotProperty& temp  = device.addFloat("temperature", "°C", 1);
IotProperty& relay = device.addBool("relay").onSet([](IotProperty&, const String& v) {
  digitalWrite(2, v == "true");
  return true;                       // принять команду
});

void setup() {
  Serial.begin(115200);
  pinMode(2, OUTPUT);
  device.setDebug(&Serial);
  device.setWiFi("my-wifi", "password");
  device.setServer("iot.example.com");
  device.setClaimToken("...из POST /api/devices...");
  device.setCaCert(CA_CERT);
  device.setPortal("change-me-1234");   // пароль точки доступа настройки
  if (!device.begin()) Serial.println("ошибки конфигурации — см. [iot] ОШИБКА в логе");
}

void loop() {
  device.loop();                     // вызывать постоянно, без длинных delay()
  temp.setFloat(readSensor());       // в своём темпе, например раз в 10 секунд
}
```

## Свойства

| Метод | Тип в `$meta` | Значение на проводе |
|---|---|---|
| `addBool(name)` | `boolean` | `true` / `false` |
| `addInt(name, unit)` | `integer` | `42` |
| `addFloat(name, unit, decimals)` | `float` | `21.5` (округление до `decimals`) |
| `addString(name)` | `string` | текст до 256 байт |
| `addEnum(name, {"off", "heat"})` | `string` + `"enum":[...]` | одно из значений списка |

`addEnum` оставляет в `$meta` тип `string`, поэтому веб-панель и сценарии работают с ним как со строкой,
а список уходит дополнительным полем `enum`. Команды и `setString()` со значением не из списка SDK отклоняет сам.

Имя свойства: `a-z`, `0-9`, `_`, `-`, до 32 символов, начинается с буквы. Его же проверяют ACL и ingest на сервере.
Свойство с недопустимым именем или повторным именем SDK не отправляет вовсе — ни в `$meta`, ни значениями:
`begin()` вернёт `false`, ошибки появятся в логе (`setDebug` можно вызвать и после объявления свойств)
и в `device.configErrors()`. Проверить конкретное свойство: `prop.valid()`.

Дополнительно к объявлению можно вызвать:
- `.unit("°C")` — единица измерения;
- `.range(min, max)` — для команд: значения вне диапазона SDK отклоняет сам;
- `.onSet(handler)` — делает свойство управляемым;
- `.deadband(delta)`, `.minInterval(ms)` — ограничить частоту отправки (см. ниже);
- `.persist()` — сохранять значение во флеше (см. ниже).

Установка значения: `setBool`, `setInt`, `setFloat`, `setString`. Если устройство онлайн, значение уходит сразу.
Если офлайн — после переподключения.
Без `deadband` и `minInterval` каждый вызов — это одно сообщение и одна точка в истории.

Чтение: `value()` (как строка), `boolValue()`, `intValue()`, `floatValue()`, `hasValue()`.

### Частота отправки

```cpp
device.addFloat("temperature", "°C", 1).deadband(0.2).minInterval(10000);
device.addBool("door").deadband(0);   // только при изменении
```

- `deadband(delta)` — значение уходит, только если отличается от **последнего отправленного** на `delta`
  и больше. Сравниваются уже округлённые до `decimals` значения. Для `bool`, `string` и `delta = 0` —
  при любом изменении. Медленный дрейф не теряется: накопившись до `delta`, он будет отправлен.
- `minInterval(ms)` — не чаще раза в `ms`. Промежуточные значения не копятся: когда интервал истечёт,
  уйдёт последнее.
- `value()` всегда возвращает текущее значение, даже если серверу оно ещё не отправлено.
- Не фильтруются: подтверждения команд (сервер ждёт ответа сразу) и отправка всех значений после
  (пере)подключения.

Так датчик можно опрашивать часто, хоть в каждом `loop()`, а сервер получит только существенные изменения.

### Сохранение во флеше

```cpp
IotProperty& relay = device.addBool("relay").persist().onSet([](IotProperty&, const String& v) {
  digitalWrite(RELAY_PIN, v == "true");
  return true;
});

void setup() {
  relay.setBool(false);   // по умолчанию — ДО begin()
  device.begin();         // восстановит сохранённое и вызовет onSet
}
```

- Значение записывается при каждом **изменении**, повторная установка того же значения флеш не трогает.
  Не включайте `persist()` для быстро меняющихся показаний датчиков: флеш изнашивается.
- `begin()` восстанавливает значение и вызывает `onSet` с ним, чтобы «железо» вернулось в прежнее
  состояние. Если обработчик вернёт `false`, останется значение по умолчанию. Затем значение, как обычно,
  уйдёт на сервер при подключении.
- Значение по умолчанию задавайте **до** `begin()`: `set*()` после `begin()` перезапишет восстановленное.
- Если в новой прошивке сохранённое значение не подходит (сменился тип или сузился `range`), оно пропускается.
- Все значения хранятся одной записью `pv`; на ESP32 её размер ограничен ~4000 байт NVS.
  Сброс настроек (кнопка, `resetConfig()`) стирает и их.

### Команды

```cpp
device.addInt("brightness", "%").range(0, 100).onSet([](IotProperty& p, const String& v) {
  analogWrite(LED, v.toInt() * 255 / 100);
  return true;
});
```

`v` уже приведено к типу: `"on"`, `"1"`, `"yes"` превращаются в `"true"`, float округляется до `decimals`.
Обработчик возвращает:
- `true` — значение сохраняется и отправляется серверу как подтверждение;
- `false` — серверу уходит прежнее значение, интерфейс «откатится».

Сервер тоже знает о `settable`: бэкенд не отправит команду в свойство, которое в `$meta` не помечено управляемым.

### Служебные команды

`device.enableCommands()` (до `begin()`) добавляет settable-свойство `cmd`. Команда отправляется
как обычная: `POST /api/devices/<id>/commands {"property":"cmd","value":"reboot"}`.

| Значение | Что делает |
|---|---|
| `reboot` | перезагрузка |
| `portal` | открыть портал настройки (например, чтобы сменить Wi-Fi) |
| `reset` | стереть все настройки и привязку, перезагрузиться. Дальше — только через портал и новый токен |
| `identify` | вызвать `onIdentify(cb)`: помигать светодиодом, пискнуть. Без обработчика команда отклоняется |

Подтверждение уходит серверу до выполнения. Перед перезагрузкой SDK публикует `$state = disconnected`.

Команды `cmd` получает любой, кто может управлять устройством через API. Обновление прошивки — см. «Обновление прошивки (OTA)» ниже.

## Настройки

| Метод | Назначение |
|---|---|
| `setWiFi(ssid, pass)` | Wi-Fi по умолчанию |
| `setWiFiFallback(ssid, pass)` | запасная сеть: если текущая недоступна 20 с, устройство пробует другую (и обратно) |
| `setServer(host, port = 8883)` | `PUBLIC_HOST` сервера; HTTPS для привязки всегда на 443 |
| `setClaimToken(token)` | токен для первой привязки или перепривязки |
| `setCaCert(pem)` | корневой сертификат сервера (см. ниже) |
| `setInsecure()` | без проверки сертификата — **только для отладки** |
| `setConfigButton(pin)` | удержание 3 с при включении стирает настройки (на ESP8266 для кнопки «к питанию» нужна внешняя подтяжка к земле) |
| `setPortal(apPass, timeoutSec)` | пароль точки доступа (от 8 символов) и таймаут портала. **Задайте его:** без пароля сеть открытая, и пароль Wi-Fi с claim-токеном уходят открытым текстом |
| `setDebug(&Serial)` | лог SDK |
| `enableStats(intervalSec = 60)` | служебная телеметрия (см. ниже) |
| `enableCommands()`, `onIdentify(cb)` | служебные команды (см. выше) |
| `enableOta()`, `onOtaStart(cb)` | обновление прошивки по воздуху (см. выше) |
| `onStateChange(cb)` | `Portal → WifiConnecting → Provisioning → MqttConnecting → Online` |

Значения, сохранённые через портал, важнее значений из прошивки. Чтобы вернуться к прошитым, сбросьте
настройки кнопкой или вызовите `device.resetConfig()`.

Прочее:
- `device.publishState("sleeping")` — свой `$state`: только `ready`, `sleeping`, `alert`
  (`init`, `lost`, `disconnected` выставляют SDK и брокер);
- `device.startPortal()` — открыть портал вручную, например по долгому нажатию.
  Перед этим SDK публикует `$state = disconnected`: при штатном отключении брокер LWT не шлёт;
- `device.deepSleep(seconds)` — глубокий сон (см. ниже);
- `device.pending()` — есть значения, ещё не отправленные серверу;
- `device.online()`, `device.state()`, `device.deviceId()`.

### Глубокий сон

```cpp
void loop() {
  device.loop();
  if ((device.online() && !device.pending()) || millis() > 30000) device.deepSleep(300);
}
```

`deepSleep()` отправляет накопленные значения (не дожидаясь `minInterval`), публикует `$state = sleeping`,
штатно отключается — LWT `lost` не срабатывает, и сервер видит плановый сон, а не обрыв, — и засыпает.
`0` — спать до внешнего пробуждения. После пробуждения устройство стартует заново с `setup()`.
На ESP8266 для пробуждения по таймеру GPIO16 соединяют с RST. Полный пример — `examples/DeepSleep`.

### Блокирующие операции

`loop()` возвращает управление быстро, кроме следующих моментов:

| Что | Сколько может занять | Когда |
|---|---|---|
| TLS-подключение к брокеру | обычно 1–3 с, при плохой сети до ~10 с | при подключении и переподключении |
| Привязка (HTTPS `POST /api/provision`) | до ~18 с | только при первой привязке и новом токене |
| Загрузка OTA | десятки секунд | только по команде обновления из панели |
| Удержание кнопки сброса | до 3 с | в `begin()`, если задан `setConfigButton` |

Синхронизация времени (NTP) не блокирует: SDK ждёт её до 5 секунд, но `loop()` всё это время
возвращает управление скетчу.

Если скетчу нужна реакция без задержек (кнопка, ШИМ, защита нагревателя), не полагайтесь на `loop()`:
используйте прерывания (`attachInterrupt`), аппаратные таймеры, а на ESP32 — отдельную задачу FreeRTOS
(`xTaskCreatePinnedToCore`) для критичной логики. Все вызовы `device.*` и `prop.set*()` делайте из одной задачи.

### Служебная телеметрия

`device.enableStats(60)` (до `begin()`) добавляет обычные свойства — они попадают в `$meta`,
историю и интерфейс без доработок сервера:

| Свойство | Тип | Когда отправляется |
|---|---|---|
| `rssi` | integer, dBm | при подключении и раз в `intervalSec` |
| `uptime` | integer, s | то же; не сбрасывается при переполнении `millis()` через 49 дней |
| `free_heap` | integer, B | то же |
| `reset_reason` | string | при подключении и изменении: `power_on`, `software`, `panic`, `watchdog`, `brownout` (ESP32), `deep_sleep`, `external`, `unknown` |
| `ip` | string | при подключении и изменении |

Если в скетче уже есть свойство с одним из этих имён, служебное игнорируется (ошибка в `configErrors()`),
а ваше продолжает работать.

### Сертификат

- **Let's Encrypt** — вшейте ISRG Root X1: `curl -s https://letsencrypt.org/certs/isrgrootx1.pem`.
  Это корневой сертификат: при продлении сертификата сервера раз в 60–90 дней прошивку менять не нужно.
- **Самоподписанный** — вшейте `data/certbot/conf/live/iot/fullchain.pem` с сервера.

### Когда открывается портал

- нет Wi-Fi, адреса сервера или (нет привязки и нет токена);
- Wi-Fi не подключился за минуту после включения (если устройство ещё ни разу не было онлайн;
  с запасной сетью за это время пробуются обе);
- сервер 3 раза подряд отклонил токен — он просрочен или уже использован;
- брокер 5 раз подряд отверг учётку (`not authorized`) — устройство удалили или перепривязали;
- команда `portal` или вызов `startPortal()`.

Учётку при отказе брокера SDK **не стирает**: это мог быть сбой сервера, и после таймаута портала
устройство снова пробует подключиться. Если устройство действительно удалили, введите в портале новый токен.

На странице портала видно, **почему** он открылся, а также ID устройства, MAC и версия прошивки.
Поле сети подсказывает найденные сети (сильные первыми); поиск идёт в фоне и не блокирует страницу,
список обновляется по ссылке «Обновить список сетей». В блоке «Запасная сеть» задаётся вторая сеть.

Пока портал открыт, подключение к Wi-Fi приостановлено: иначе попытки подключения гоняют радио по каналам,
и телефон отваливается от точки доступа. После таймаута портала подключение возобновляется.

В форме портала пустой пароль означает «не менять»; чтобы перейти на открытую сеть, отметьте
«Сеть без пароля». Имя сети сохраняется как введено, включая пробелы по краям.

### Хранение настроек

Учётка MQTT и настройки из портала сохраняются каждая одной записью (`cred` и `cfg`), поэтому сбой
питания не оставит их «наполовину» — например, новый Wi-Fi со старым паролем.
На ESP8266 файл настроек записывается во временный и атомарно переименовывается поверх старого:
на флеше всегда есть целая версия. Настройки и учётки, сохранённые прежними версиями, читаются.

## Обновление прошивки (OTA)

```cpp
device.enableOta();                                        // по умолчанию выключено
device.onOtaReboot([]() { digitalWrite(RELAY_PIN, LOW); }); // необязательно: перед перезагрузкой
device.onOtaStart([]() { return !heating; });               // необязательно: false — отказаться сейчас
```

1. Соберите прошивку с новой версией в конструкторе: `IotDevice device("Кухня", "1.1.0")`.
   В Arduino IDE: **Скетч → Экспорт бинарного файла**, нужен `<скетч>.ino.bin` (не `merged`, не `bootloader`).
   В PlatformIO: `.pio/build/<env>/firmware.bin`.
2. Панель: **Настройки → Прошивки → Загрузить**, затем на странице устройства **Обновить прошивку**.
3. Устройство получает команду `dev/<id>/$ota/set` (retained — дойдёт и после переподключения), скачивает файл
   по одноразовой ссылке со своего же сервера через TLS с тем же сертификатом, проверяет MD5 и перезагружается.
   Ход и итог видны в панели: `downloading` с процентами → `rebooting` → `done` (или `failed` с причиной).

Защита от сбоев:
- задание запоминается до скачивания: если новая прошивка не запустится и загрузчик вернёт старую,
  повторно то же задание выполняться не будет, а сервер получит `failed` «ожидалась версия X»;
- команда с той же версией, что уже стоит, сразу отвечает `done`;
- `onOtaStart` вернул `false` (идёт нагрев, открыт клапан) — образ не скачивается, сервер получает `failed`,
  задание не повторяется: запустите обновление из панели позже;
- адрес в команде — только путь `/api/ota/…`: хост и сертификат устройство берёт из своих настроек;
- на ESP8266 на время скачивания закрывается MQTT (двух TLS-соединений память не выдерживает),
  проценты в панели не обновляются, итог придёт после переподключения.

Нужна схема разделов с двумя слотами приложения (на ESP32 это по умолчанию; на ESP8266 — флеш от 1 МБ
и прошивка меньше половины свободного места: **Tools → Flash Size** с OTA).

## Перепривязка

1. `POST /api/devices/<id>/claim` — новый токен. Старый пароль сразу перестаёт работать.
2. Передайте токен устройству: через портал (кнопка при включении) или новой прошивкой с `setClaimToken`.
3. SDK заметит, что токен отличается от использованного, и привяжется заново.

## Проверка на ПК

```bash
cd test/host
make test         # юнит-тесты протокола (топики, парсинг, $meta, JSON, файл настроек)
make device       # поведение: SDK и настоящий PubSubClient против симулятора (время, Wi-Fi, NVS, HTTP,
                  # поддельный MQTT-брокер, веб-сервер портала)
make compile      # сборка SDK и всех примеров под ESP32 с заглушками и настоящим PubSubClient
make compile8266  # то же под ESP8266 + проверка хранилища на LittleFS
```

Заглушки повторяют сигнатуры arduino-esp32 3.x и esp8266/Arduino 3.x. Это проверка API, типов и логики SDK,
а не замена сборки под плату: радио, TLS и флеш здесь не настоящие. Нужны `g++` и `make`
(в WSL: `sudo apt install g++ make`).

## Ограничения

- ESP32 и ESP8266 на Arduino core 3.x; другие платы не поддерживаются.
- PubSubClient публикует с QoS 0: при обрыве связи значение может потеряться (команды подписаны с QoS 1).
- OTA не откатывается автоматически, если новая прошивка запустилась, но не может подключиться
  к серверу: проверяйте образ на одном устройстве, прежде чем обновлять остальные.
- Свойства объявляются до `begin()`. Добавленное позже не попадёт в `$meta` до переподключения.
