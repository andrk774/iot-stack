# IoT Stack — самохостинговая платформа по принципам 2Smart

Платформа для своих устройств на одном VPS: веб-панель (ставится на телефон как приложение), привязка устройств,
MQTT с TLS и ACL, история показаний за 2 года, сценарии автоматизации, уведомления в Telegram, вебхуки и push,
обновление прошивок по воздуху, общий доступ для семьи, Алиса, мосты для Zigbee/ESPHome/Tasmota/Shelly/любого MQTT,
двухфакторный вход, бэкапы, SDK для ESP32, ESP8266, Node.js и Python.

```
ESP32/ESP8266/Pi ──mqtts:8883──┐                       ┌── auth/ACL (HTTP) ── backend :8001
мосты (дома) ─────mqtts:8883───┼─► nginx ─► EMQX :1883 ◄┘
браузер ──────────wss /mqtt────┘    │          │  шина dev/<id>/…, bridge/<id>/$state
браузер ──────────https /api ───────┴─► backend :8000 (REST, JWT, мосты, сценарии)
                                         │
              ingest ($share, пачки) ────┼──► PostgreSQL + TimescaleDB ◄── backup (pg_dump → диск/S3)
              scenarios (правила, cron) ─┘         ▲ NOTIFY scenarios_changed
```

| Сервис | Аналог в 2Smart | Что делает |
|---|---|---|
| `emqx` | `2smart-emqx` | MQTT-брокер. Логин и ACL спрашивает у бэкенда по HTTP |
| `postgres` | `2smart-mysql` + `influxdb` | Пользователи, устройства, мосты, сценарии, уведомления; телеметрия в hypertable (сжатие через 7 дней, удаление через 90) |
| `backend` | `client-dashboard-be` | REST API, сеансы и 2FA, привязка устройств, команды, OTA, мосты, сценарии, общий доступ, рассылка уведомлений, Алиса, хуки EMQX, миграции БД |
| `ingest` | `time-series-service` | Пишет значения в БД пачками раз в секунду через журнал на диске, отслеживает состояние мостов |
| `scenarios` | `scenario-runner` | Правила «если — то», расписания, уведомления |
| `nginx` | `2smart-nginx` | Панель, HTTPS, CSP, rate limit, TLS для MQTT (8883), WebSocket `/mqtt` |
| `web/public` | `2smart-ui` | Веб-панель и PWA без сборки: главная, комнаты, живые данные, графики, сценарии, мосты, настройки |
| `bridge-*` | мосты `zigbee`, `esphome`, `mqtt-adapter` | zigbee2mqtt, ESPHome (MQTT discovery), Tasmota, Shelly, произвольный MQTT по правилам |
| `backup` | `backup-service` | Ежедневный `pg_dump`, ротация, выгрузка в S3-совместимое хранилище |
| `certbot` | `certbot-bridge` | Сертификат Let's Encrypt и его продление |

Сознательно не повторено из 2Smart: `docker.sock` в контейнерах, самообновление, маркетплейс мостов —
это даёт контейнерам root на хосте. Мосты включаются профилями Compose, обновление — `docker compose pull/build`.

## Установка на VPS

Нужны Ubuntu/Debian, 2 ГБ RAM (лучше 4) и Docker с Compose v2.

```bash
curl -fsSL https://get.docker.com | sh
sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw allow 8883/tcp && sudo ufw enable

scp -r iot-stack user@vps:~/ && ssh user@vps
cd ~/iot-stack && ./setup.sh
```

`setup.sh` спросит домен:
- **есть домен** (A-запись указывает на VPS) — сертификат Let's Encrypt с автопродлением;
- **нет домена** — самоподписанный сертификат на IP на 10 лет; его нужно вшить в прошивки.

Секреты генерируются в `.env` (права 600). При обновлении со старой версии `setup.sh` сам допишет
в `.env` новые переменные. Схема БД обновляется автоматически при старте бэкенда (`backend/migrations`).

Затем откройте `https://<host>/` и зарегистрируйтесь. После этого можно выставить
`ALLOW_REGISTRATION=false` в `.env` и выполнить `docker compose up -d backend`.

EMQX Dashboard открыт только на localhost сервера:
`ssh -L 18083:127.0.0.1:18083 user@vps`, затем `http://localhost:18083` (admin / `EMQX_DASHBOARD_PASSWORD`).

## Веб-панель

- **Главная** — своя у каждого пользователя: плитки с показаниями и переключателями (☆ на странице устройства или
  «Настроить → Добавить плитку», порядок стрелками), сводка «в сети / без связи», кнопки ручных сценариев.
- **Устройства** — по комнатам (кнопка «Комнаты»: добавить, переименовать, порядок), с текущими значениями;
  значения обновляются вживую по MQTT over WSS. Комната выбирается на странице устройства.
- **Устройство** — плитки строятся из `$meta`: переключатели для `boolean`, выпадающий список для `enum`, поля ввода для чисел и строк
  с учётом `min`/`max`, график за час/сутки/неделю/месяц/3 месяца/год: до 4 линий (свойства этого устройства и,
  для сравнения, других), выгрузка в CSV для Excel; комната, перепривязка, удаление.
- **Сценарии** — редактор правил, включение и выключение, ручной запуск, журнал запусков.
- **Мосты** — создание, токен и готовые строки для `.env`, смена токена.
- **Уведомления** — то, что прислали сценарии.
- **Настройки** — каналы уведомлений, общий доступ, безопасность, прошивки для OTA.

Панель подписывается на брокер как пользователь `u:<id>` с JWT вместо пароля и может только читать
топики своих устройств. Команды идут через REST, где сервер проверяет `settable`.

Разработка панели без сервера: `node web/dev/mock-server.js` → `http://localhost:8080`
(данные в памяти, мини-брокер MQTT over WebSocket).

## Топики

```
dev/<id>/$state       init | ready | lost | sleeping | alert | disconnected   (retained)
dev/<id>/$meta        {"name":…, "fw":…, "props": {"relay": {"type":"boolean","settable":true}, …}}  (retained)
dev/<id>/<prop>       значение: число, true/false или текст до 256 байт
dev/<id>/<prop>/set   команда (публикуют только бэкенд и сценарии)
dev/<id>/$ota/set     команда обновления прошивки (бэкенд, retained); dev/<id>/$ota — ход и итог от устройства
bridge/<bid>/$state   состояние моста (LWT); при потере — его устройства помечаются «нет связи»
```

| Кто подключается | Логин | Права |
|---|---|---|
| устройство | `d<16 hex>` = client id | публикует своё поддерево, подписан на свои `…/set` |
| мост | `b<16 hex>` = client id | то же для устройств, которые он зарегистрировал |
| веб-панель | `u:<uuid>`, пароль = JWT, client id `web-<uuid>-<случайное>` | только подписка на свои устройства |
| `backend`, `ingest`, `scenarios` | из `.env` | superuser |

Отзыв доступа действует сразу. При перепривязке или удалении устройства, смене токена или удалении моста
бэкенд меняет пароль в БД и разрывает уже открытую сессию через REST API EMQX (`DELETE /api/v5/clients/<id>`).
Ключ API (`EMQX_API_KEY`/`EMQX_API_SECRET`) генерирует `setup.sh` и кладёт в `data/emqx/api_keys.conf`.

Плохое сообщение не останавливает запись: значения и `$meta` с нулевым байтом отбрасываются ещё в ingest,
а если PostgreSQL всё же отклонит строку, ingest находит её делением пачки пополам и выбрасывает только её
(счётчик `rejected` в логе). Пачка целиком возвращается в буфер только при ошибке связи с БД.

Принятое сообщение сначала дописывается в журнал на томе `ingest-journal` — до того, как брокер получит
подтверждение, — и удаляется оттуда после записи пачки в БД. Падение или перезапуск ingest не теряет данные:
при старте журнал проигрывается заново (в логе «journal: восстановлено N событий»). Если процесс упадёт ровно
между записью в БД и очисткой журнала, несколько значений запишутся дважды — это безопаснее потери.
Пока БД недоступна, журнал растёт до 64 МБ, дальше данные копятся только в памяти.

## Хранение телеметрии

Сырые значения хранятся 90 дней (сжатие через 7 дней). Почасовые агрегаты — среднее, минимум, максимум, число точек —
два года: это непрерывный агрегат TimescaleDB `telemetry_hourly`, обновляется в фоне каждые 30 минут, а последний
час добирается из сырых данных на лету. Графики с шагом от часа и выгрузки за месяцы и годы берут данные оттуда.
При первом запуске новой версии бэкенд один раз заполняет агрегат по уже накопленной истории.

## Сценарии

Запуск:
- изменение свойства: `>`, `≥`, `<`, `≤`, `=`, `≠` срабатывают на переходе «не выполнено → выполнено»;
  `изменилось` — на каждое новое значение;
- то же, но «держится дольше N минут» (кратковременный скачок не запускает) и с гистерезисом
  (порог 30, гистерезис 2: повторно — только после падения ниже 28);
- переход устройства в состояние (`нет связи`, `тревога`, …);
- нет данных от устройства или одного его свойства дольше N минут (разрядился датчик на батарейке);
- расписание cron в своём часовом поясе (`0 7 * * 1-5`);
- только вручную.

Дополнительные условия — значение свойства, состояние устройства (в состоянии / не в нём), время суток с днями
недели (окно через полночь, например 22:00–07:00, считается от дня, когда началось); выполнены все или хотя бы одно.
Проверяются по последним известным значениям. Действия выполняются по порядку:
установить свойство, уведомить (`{device}`, `{property}`, `{value}`, `{scenario}` в тексте), пауза до часа.
Защита от зацикливания: пока сценарий выполняется, повторно он не запускается; не больше 30 запусков в минуту;
настраиваемый интервал «не запускать повторно».

Журнал запусков на странице сценария: когда и чем запущен (значение, состояние, «нет данных», расписание, вручную),
что сделал каждый шаг и чем закончился, а также пропуски — условия не выполнены, пауза между запусками, слишком
часто. Пропуски пишутся не чаще раза в минуту на сценарий; хранятся последние 200 записей.

## Аккаунт и безопасность

**Настройки → Безопасность:**
- смена пароля (нужен текущий; остальные сеансы при этом завершаются);
- двухфакторная защита TOTP: QR-код для приложения-аутентификатора, 10 одноразовых кодов восстановления.
  Повторно использовать тот же код нельзя;
- список сеансов (браузер, IP, последняя активность), завершение любого или всех, кроме текущего.

Токен панели ссылается на сеанс в БД, поэтому выход, завершение сеанса и смена пароля действуют сразу:
и для REST, и для живого MQTT-подключения панели (EMQX разрывает его, панель переподключится уже с действующим токеном).
После обновления на эту версию всем нужно войти заново (старые токены были без сеанса).

### API-токены

**Настройки → API-токены** — для скриптов, Home Assistant, Node-RED. Токен `iot_…` передаётся как
`Authorization: Bearer iot_…` и действует от имени владельца (в том числе в домах, куда его пригласили).
«Только чтение» пропускает лишь GET. Срок — бессрочно, 30, 90 дней или год; отзыв действует сразу.
Менять пароль, сеансы, 2FA, токены, каналы уведомлений, участников дома и связку с Алисой токеном нельзя — только из панели.
Тот же токен годится как MQTT-пароль для живых данных (`wss://<host>/mqtt`, логин `u:<id>`,
client id `web-<id>-<4–16 строчных букв и цифр>`), подписка только на чтение.

Забыли пароль (сброс по почте платформа не делает):
```bash
docker compose exec backend node scripts/reset-password.js you@example.com           # новый временный пароль
docker compose exec backend node scripts/reset-password.js you@example.com --no-2fa  # и выключить 2FA
```

## Общий доступ

**Настройки → Общий доступ → Пригласить:** одноразовая ссылка `https://<host>/#/join/<код>` (7 дней) с ролью:

| Роль | Может |
|---|---|
| просмотр | видеть устройства, графики, сценарии, ленту уведомлений |
| управление | ещё отправлять команды устройствам и запускать сценарии |
| администратор | ещё добавлять, переименовывать и удалять устройства, сценарии, мосты; обновлять прошивки |
| владелец | всё, плюс участники и приглашения |

По ссылке можно зарегистрироваться, даже если `ALLOW_REGISTRATION=false`. Уведомления дома получают все участники —
каждый по своим каналам и со своим порогом. Каналы уведомлений, пароль и 2FA у каждого свои. Если доступ есть
к нескольким домам, панель группирует устройства по дому, а при создании устройства, сценария, моста или загрузке
прошивки спрашивает, в какой дом. Сценарий работает только с устройствами своего дома.
Убранный участник теряет доступ сразу, в том числе к живым данным по MQTT.

## Уведомления

Действие сценария «Уведомить» всегда пишет в ленту панели, а в **Настройки → Куда присылать уведомления**
подключаются внешние каналы. У каждого канала свой порог: все, «внимание и тревога» или только тревога.

- **Telegram, платформенный бот.** Создайте бота у @BotFather и впишите токен в `.env` (`TELEGRAM_BOT_TOKEN`),
  перезапустите `backend`. В панели кнопка «Подключить Telegram» откроет бота со ссылкой `?start=<код>`
  (действует 15 минут). Бот работает через long polling: вебхук и открытые порты не нужны. `/stop` в чате отключает его.
- **Telegram, свой бот:** токен бота и id чата прямо в панели, без настройки сервера.
- **Вебхук:** POST с JSON `{id, level, message, scenario_id, scenario_name, created_at}` на https-адрес.
  Подпись: `X-Iot-Signature: sha256=HMAC_SHA256(secret, "<X-Iot-Timestamp>.<тело>")`, секрет показывается один раз.
  Адреса внутренних сетей (10/8, 192.168/16, 127/8, docker-сеть и т. п.) запрещены — проверка идёт после DNS,
  редиректы не выполняются.
- **Email:** нужен SMTP в `.env` — `SMTP_URL` (`smtps://user:pass@host:465` или `smtp://user:pass@host:587`
  со STARTTLS; без TLS пароль не отправляется) и `SMTP_FROM`. Адрес подтверждается кодом из письма — иначе через
  сценарии можно было бы слать письма на чужой ящик; повторный код — не чаще раза в минуту. Адрес, который сервер
  почты отклонил (5xx), выключает канал.
- **Push в браузер** — см. «Приложение на телефон (PWA)».

## Приложение на телефон (PWA)

Панель устанавливается как приложение: Android/Chrome — «Установить приложение» в меню браузера,
iPhone — «Поделиться» → «На экран „Домой“». Открывается без адресной строки, со своей иконкой; без сети показывает
последнюю загруженную версию панели (данные — когда связь вернётся).

**Push-уведомления:** Настройки → Куда присылать уведомления → **Push в этот браузер**. Приходят и при закрытой панели;
тревоги остаются на экране, пока их не смахнут. Каждый браузер или телефон — отдельный канал со своим порогом.
На iPhone push работает только в установленной панели (iOS 16.4+).

Сервер создаёт ключи VAPID сам при первом запуске (таблица `server_settings`, попадает в бэкапы). Шифрование —
RFC 8291 (aes128gcm), подпись — VAPID (RFC 8292), без сторонних библиотек. Контакт для push-сервисов —
`https://<PUBLIC_HOST>`, можно задать `WEBPUSH_SUBJECT=mailto:you@example.com`.

Рассылка идёт сразу после записи в ленту (NOTIFY `notification_new`), при сбое — одна повторная попытка.
Если бот заблокирован в чате или браузер отозвал подписку, канал выключается, причина видна в списке.
Если бэкенд был выключен больше часа, накопившиеся уведомления остаются только в ленте.
Если `api.telegram.org` с VPS недоступен, укажите зеркало Bot API в `TELEGRAM_API_URL`.

## Обновление прошивок (OTA)

1. **Настройки → Прошивки для OTA:** загрузите `.bin` приложения (до `FIRMWARE_MAX_MB`, по умолчанию 4 МБ)
   с названием и версией — той же, что в скетче. Файл хранится в PostgreSQL и попадает в бэкапы.
2. На странице устройства: **Прошивка → Обновить прошивку**. Бэкенд создаёт задание и публикует retained-команду
   `dev/<id>/$ota/set` с путём `/api/ota/<токен>` (ссылка действует сутки и только пока задание не завершено),
   размером, MD5 и версией. Устройство, которое сейчас не в сети, получит её при подключении.
3. Устройство (Arduino SDK, `device.enableOta()`) скачивает файл, проверяет MD5, перезагружается и сообщает
   ход и итог в `dev/<id>/$ota`; бэкенд обновляет задание и снимает команду. Новое задание отменяет незавершённое.

Работает для устройств с прямым подключением; устройства мостов обновляются своими средствами
(zigbee2mqtt OTA, ESPHome).

## Алиса

Устройства платформы появляются в «Доме с Алисой»: управление голосом («Алиса, включи свет на кухне») и в приложении.
Нужен частный навык умного дома в [консоли Яндекс Диалогов](https://dialogs.yandex.ru/developer) — публиковать его
в каталоге не обязательно, он работает для вашего аккаунта Яндекса.

1. В `.env` придумайте `YANDEX_CLIENT_ID` (например, `iot-home`) и `YANDEX_CLIENT_SECRET` (32+ случайных символа),
   перезапустите `backend` (`docker compose up -d backend`).
2. В консоли Диалогов: **Создать диалог → Умный дом**. Endpoint URL — `https://<host>/yandex`.
3. **Связка аккаунтов**: идентификатор и секрет приложения — значения из шага 1; URL авторизации —
   `https://<host>/oauth/authorize`; URL для получения и обновления токена — `https://<host>/oauth/token`.
   Эти же адреса показаны в панели: Настройки → Алиса.
4. В приложении «Дом с Алисой»: **+ → Устройство умного дома → ваш навык → Привязать**. Откроется панель,
   войдите и нажмите «Разрешить».

Как устройства видны в Яндексе: управляемое boolean-свойство — «вкл/выкл» (розетка, если есть мощность; свет —
если в названии «свет»/«лампа» или есть яркость; иначе выключатель); яркость/диммер и позиция штор — проценты;
уставка температуры — термостат; датчики с единицами — температура, влажность, мощность, напряжение, ток,
энергия, освещённость, CO2, давление, заряд. Второе и следующие реле устройства — отдельные устройства.
Названия и комнаты — из панели. Участники дома с ролью «просмотр» видят устройства, но не управляют ими.

Чтобы приложение обновляло состояния сразу (а не только при открытии), задайте `YANDEX_SKILL_ID` и
`YANDEX_SKILL_TOKEN` (OAuth-токен владельца навыка) — бэкенд будет отправлять изменения в сервис уведомлений Яндекса.
Отвязать: Настройки → Алиса или удалить навык в приложении Яндекса.

## Мосты

1. В панели: **Мосты → Добавить мост**, выберите тип. Панель покажет `BRIDGE_ID` и токен (один раз).
2. Запустите мост там, где виден внешний брокер:
   - **дома** рядом с zigbee2mqtt/ESPHome — `bridges/home/` (mosquitto + zigbee2mqtt + мосты; к VPS ходят по https и mqtts,
     наружу из дома ничего открывать не нужно):
     ```bash
     cd bridges/home && cp .env.example .env   # PUBLIC_HOST и выданные ID/токены
     docker compose --profile zigbee up -d
     ```
   - **на VPS**, если внешний брокер доступен оттуда: впишите `ZIGBEE_BRIDGE_ID`/`…_TOKEN`/`…_MQTT_URL` в `.env`
     и `docker compose --profile zigbee up -d` (так же `esphome`, `generic`).
3. Устройства появятся в панели сами, с типами и единицами из zigbee2mqtt или discovery.

| Тип | Откуда устройства | Что поддерживается |
|---|---|---|
| `zigbee2mqtt` | `<base>/bridge/devices` | binary, numeric (с диапазоном), enum, text; свойства внутри light/switch/climate/cover/lock; доступность |
| `esphome` | MQTT discovery (`homeassistant/…/config`) | sensor, binary_sensor, switch, number, select, light (вкл/выкл и яркость в JSON-схеме); доступность. Нужен компонент `mqtt:` в ESPHome, пример — `bridges/home/esphome-example.yaml` |
| `tasmota` | discovery Tasmota 9+ (`tasmota/discovery/<MAC>/config`) или список Topic | реле `power`/`power1…N`, `dimmer`, все числовые датчики из `SENSOR` (энергия, климат, освещённость…) с единицами, RSSI, `LWT` |
| `shelly` | Gen2/Gen3: `<id>/status/<компонент>`, `events/rpc`; Gen1: `shellies/<id>/…` | реле и свет (команды через RPC / `command`), мощность, напряжение, ток, энергия в кВт·ч, температура, шторы (позиция), входы, датчики H&T, батарея; `online` |
| `generic` | правила в настройках моста | топик → свойство, ключ в JSON, `payload_on/off`, топик команды |

Удалённое в панели устройство моста запоминается: мост больше не добавляет его снова. Вернуть — **Мосты → Скрытые**.

Ограничения: ESPHome native API (порт 6053) не используется — только MQTT. В zigbee2mqtt не поддерживаются
составные свойства (цвет XY, расписания термостатов).

## Бэкапы

Сервис `backup` каждый день в `BACKUP_TIME` делает `pg_dump` в `./data/backups`, проверяет файл и хранит
`BACKUP_KEEP_DAYS` последних дней. Если заданы `S3_*`, копия уходит в S3-совместимое хранилище
и там хранится `S3_KEEP_DAYS` дней.

```bash
docker compose exec backup backup.sh now     # бэкап сейчас
docker compose exec backup backup.sh list    # что есть локально и в S3

docker compose stop backend ingest scenarios
docker compose exec backup restore.sh iot-2026-10-23T0330.dump      # или s3://bucket/iot-backups/…
docker compose start backend ingest scenarios
```

`.env` в бэкап не входит — храните его копию отдельно: без него не прочитать учётки сервисов.

## SDK для устройств

| SDK | Где | Для чего |
|---|---|---|
| `sdk/arduino/IotDevice` | Arduino IDE / PlatformIO | ESP32 и ESP8266 (0.4.0): привязка, портал настройки Wi-Fi и токена, MQTT over TLS, свойства с deadband/minInterval и сохранением во флеше, служебные команды и телеметрия, глубокий сон, OTA из панели. Для установки по ссылке — отдельный репозиторий [andrk774/IotDevice](https://github.com/andrk774/IotDevice) |
| `sdk/node` | Node.js 18+ | Raspberry Pi и любой Linux |
| `sdk/python` | Python 3.9+, paho-mqtt 2 | Raspberry Pi и любой Linux |

Во всех трёх одинаково: объявить свойства, повесить обработчик команд, `start()`/`begin()`.
Учётка выдаётся по одноразовому claim-токену из **Устройства → Добавить устройство** и сохраняется на устройстве.

## API

```bash

  -d '{"email":"me@example.com","password":"long-password"}' | jq -r .token)
A="authorization: Bearer $TOKEN"

curl -s $H/api/devices -H "$A"
curl -s $H/api/devices -H "$A" -H 'content-type: application/json' -d '{"name":"Кухня"}'      # -> claim_token
```

### Мониторинг (Prometheus)

`https://<host>/metrics` с заголовком `Authorization: Bearer <METRICS_TOKEN>` (токен генерирует `setup.sh`;
пустой — эндпоинт выключен). Одна точка сбора на всю платформу: бэкенд добавляет к своим метрикам сводку из БД,
статистику EMQX и метрики ingest и scenarios из внутренней сети (`:9100/metrics`, наружу не публикуется).

```yaml
scrape_configs:
  - job_name: iot
    scheme: https
    authorization: { credentials: <METRICS_TOKEN> }
    static_configs: [{ targets: ['<host>'] }]
```

| Метрика | Что показывает |
|---|---|
| `iot_up{service}` | доступность backend, emqx, ingest, scenarios |
| `iot_emqx_connections`, `iot_emqx_messages_*_total`, `iot_emqx_auth_failures_total` | подключения и трафик брокера |
| `iot_ingest_written_rows_total`, `…_dropped_rows_total`, `…_rejected_rows_total` | записано / выброшено при переполнении / отклонено БД |
| `iot_ingest_buffered_rows`, `iot_ingest_journal_bytes` | ждут записи в БД; растут — база не принимает данные |
| `iot_scenarios_runs_total{status}`, `iot_scenarios_action_errors_total{type}` | запуски и ошибки действий сценариев |
| `iot_notify_deliveries_total{channel,result}`, `iot_notifications_queued`, `iot_channels_failing` | доставка уведомлений |
| `iot_devices{state}`, `iot_users`, `iot_scenarios_failing` | сводка из БД |
| `iot_backend_http_requests_total{code}` | ответы API по классу |

## Разработка и тесты

```bash
devtools/test-all.sh                                          # всё без БД
PG_TEST_URL=postgres://iot@127.0.0.1:5432/postgres devtools/test-all.sh   # плюс реальный PostgreSQL
```

На Windows запускайте из Git Bash. Наборы, для которых нет инструментов, помечаются пропущенными, а не упавшими:
`sdk/python` нужен Python 3.9+ (заглушка Microsoft Store не подходит), `sdk/arduino` — `g++` и `make`
(например, из MSYS2: `pacman -S mingw-w64-ucrt-x86_64-gcc make`). Проверка прав файла учётки (0600)
на Windows не выполняется — там их нет. Интеграционный PostgreSQL удобно поднять так:
`docker run -d -p 5432:5432 -e POSTGRES_USER=iot -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16`.

Что проверяется: ACL и хуки EMQX, все маршруты API на настоящем PostgreSQL 16 (TimescaleDB-функции заменены
заглушкой), миграции, ingest, движок сценариев и cron с часовыми поясами, адаптеры мостов на реальных форматах
zigbee2mqtt и ESPHome, MQTT-кодек панели, Node- и Python-SDK с подменённым транспортом, Python-SDK против
настоящего paho-mqtt, Arduino-SDK под ESP32 и ESP8266 с заглушками ядра и настоящим PubSubClient, ротация бэкапов
и `pg_dump`, валидность `docker-compose.yml`. Панель проверялась в headless Chromium на демо-сервере
с той же политикой CSP, что в продакшене.

Что не проверялось здесь: запуск контейнеров (Docker-демона не было), конфигурации nginx и EMQX на живых
образах, сборка прошивок настоящим тулчейном, работа с реальными zigbee2mqtt/ESPHome и S3.
Первый запуск на VPS — это и есть интеграционный тест: пришлите `docker compose logs`, если что-то не поднимется.

## Ограничения

- Без ключа API EMQX (старый `.env` без `./setup.sh`) отзыв доступа не разрывает открытые сессии — бэкенд пишет об этом при старте.
- Нативного мобильного приложения нет — панель ставится на телефон как PWA.
